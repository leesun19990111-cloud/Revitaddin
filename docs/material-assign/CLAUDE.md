# 재료 지정 (Material Assign)

## 2026-10-06 v95 — 재료 변경 시 복합 구조 설정 보존

- 사용자 실모델에서 재료 지정 후 구조 재료 체크가 해제됨을 확인했다. 원인은 `MaterialSlotFinder.Apply`가 레이어를 새로 만들고 `SetLayers`로 전체를 교체한 것이다. `SetLayers`는 구조를 초기화하며 구조 재료 인덱스를 지운다. 아래 과거의 “재료 setter가 없어 레이어를 재생성해야 한다”는 설명은 잘못된 판단이었다.
- 기존 `CompoundStructure`에 `SetMaterialId(slot.LayerIndex, newMaterialId)`만 호출하고 `SetCompoundStructure`로 반영한다. 레이어 수/순서/두께/기능·우선순위/구조 재료/가변 레이어/코어 경계/감싸기/데크/수직 영역은 수정하지 않는다. 인수는 **LayerId가 아니라 0부터 시작하는 레이어 배열 인덱스**다. 재료만 바꾸는 경로에 SetLayers나 새 CompoundStructureLayer를 다시 넣지 말 것.
- NAMER 재료 병합의 동일한 전체 교체도 함께 수정했다. 기존 재료 재조회 검증과 트랜잭션 정책은 유지한다. 인스턴스 묶음 처리·검색 규칙은 v94와 동일하다.
- 공식 근거: [CompoundStructure 가이드](https://help.autodesk.com/cloudhelp/2024/JPN/Revit-API/files/Revit_API_Developers_Guide/Revit_Geometric_Elements/Walls_Floors_Ceilings_Roofs_and_Openings/Revit_API_Revit_API_Developers_Guide_Revit_Geometric_Elements_Walls_Floors_Ceilings_Roofs_and_Openings_CompoundStructure_html.html), [SetMaterialId API](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-API-MainReference/files/html/19cb546b-1c9b-f658-7a66-4206af0b4b80.htm).
- `.codex-build/release-v95`에서 기존 73개 + 복합 구조 보존 12개 대역 검사 통과. 원본 코드에 실제 MaterialSlotFinder를 연결하고 서로 다른 LayerId/배열 인덱스, 구조·가변 레이어 연속 변경, 비대상 재료·속성 보존, 잘못된 인덱스, 예전 SetLayers가 설정을 지우는 대조군을 검사한다. NAMER 경로는 금지 호출 재발 검사 및 5개 연도 빌드로 확인하며 실제 Revit 병합 실행 검증은 아니다.
- 이미 해제되어 저장된 설정은 새 버전으로 자동 복원할 수 없다. 사용자의 원래 설정을 추측해 지정하지 말 것. 실행 취소가 가능하면 되돌리거나 백업/원래 유형과 비교해 복원해야 한다. 설치 후 복사 모델의 유형 편집에서 변경 전후 구조 재료·가변·기능·우선순위·두께·코어를 실제 확인할 것.

## 2026-10-06 v94 — 유형별 인스턴스 재료 검색·일괄 지정

- 사용자 확정: 인스턴스별 행 대신 **같은 유형·재료 매개변수별 그룹**으로 표시한다. 모두 같은 재료면 재료명, 다르면 `<다양함>`이며 수정은 그 유형의 인스턴스 전체에 적용한다. 유형명 문자열이 아니라 **TypeId+SlotKind+ParameterId**로 묶어 동명 다른 패밀리/유형과 유형·인스턴스 매개변수를 섞지 않는다.
- `MaterialSlotFinder.FindAll/FindSlot/Apply`의 인자를 Element로 넓히고 `InstanceParameter`를 enum 끝에 추가했다. 기존 CompoundLayer/Parameter 의미와 Type 전용 FindEligibleTypes/FindSlotByLabel 계약은 유지한다. 비재료 스펙은 제외하고 읽기 전용도 검색에는 보인다.
- 창이 열릴 때 호스트 문서의 배치 인스턴스만 한 번 수집한다. 그룹은 각 InstanceId와 최초 MaterialId를 모두 저장한다. 미배치 유형에는 인스턴스 값이 없으며 링크 내부/페인트/패밀리 내부 형상 재료까지 검색하는 기능은 아니다. 복합 레이어와 기존 유형 재료는 그대로 별도 행이다.
- 현재 재료 필터는 그룹의 개별 재료명 중 하나라도 일치하면 포함한다. 부정 필터는 **일치 재료가 하나도 없는 그룹**만 포함한다. 재료 없음은 하나라도 명시적 Material 참조가 없는 그룹이다. 다양함에 호버하면 전체 재료명을 보여 준다. 이름 필터는 FamilyName/Type.Name 각각을 검색한다.
- 작업 재료는 그룹별 단일 값, 최초값은 HashSet으로 보관한다. 최초의 대표 재료로 통일해도 다른 원래 재료가 있으면 변경이다. 최초 공통값으로 되돌린 그룹만 diff에서 제외한다. 적용 후 체크 해제/검색 제외 시 체크 해제/누적 편집 유지/최종 적용의 2단계 규칙은 유지한다.
- 인스턴스 행에 `[인스턴스 N개 전체]`와 파라미터명을 표시하고 최종 적용 전 기본 No 확인창으로 **필터에 걸린 일부가 아니라 유형 전체**와 고유 대상 수를 알린다. 유형 결과와 InstanceResult를 구분해 기존 유형 setter에 인스턴스가 들어가지 않게 했다.
- `MaterialInstanceAssignment.TryApply`는 호출자의 Transaction 안에서 SubTransaction 하나로 유형·매개변수 묶음을 처리한다. 요소 존재/유형 유지/슬롯 존재/새 Material/읽기 전용을 검증하고, 쓰기 후 다시 읽는다. 한 건이라도 실패하면 해당 묶음을 롤백하고 다른 묶음은 계속한다. 이미 원하는 재료인 읽기 전용 요소는 쓸 필요가 없어 통과한다. 전체 outer Commit 실패는 기존처럼 알리고 기록하지 않는다. 커스텀 IFailuresPreprocessor 금지는 유지한다.
- 인스턴스 전용 사용 재료도 사용 집계에 포함한다. 미사용 표시는 실제 조사 범위를 명확히 `수집된 재료 슬롯에서 미사용`으로 표현한다(프로젝트 어디에도 쓰이지 않는다는 단정 금지). MaterialOption.ToString은 자체 ComboBox 템플릿의 선택 표시 폴백도 재료명으로 보장한다.
- 모델간 변경 반영에는 별도 MaterialInstanceAssign 기록을 남긴다. 유형 슬롯 변경으로 오인해 다른 모델에 쓰지 않도록 자동 재생은 사유와 함께 건너뛴다. 타 모델의 인스턴스 범위 매핑은 이번 범위 밖이다.
- 실제 Window/XAML/SlotFinder/InstanceAssignment를 링크한 대역 검증 33개 통과: 공통/다양함, 동명 유형 격리, 유형/인스턴스 슬롯 격리, 검색 6모드·미지정, 작업값/최종 범위, 일부 쓰기 실패 롤백, 읽기 전용·삭제·유형 변경, 무응답 Set 재검증. 실제 Revit 그룹/소유권/수식/Undo는 설치 후 복사 모델에서 확인해야 한다.

`MaterialAssignWindow.xaml(.cs)`/`MaterialAssignCommand.cs`/`MaterialSlotFinder.cs`를 건드리기 전에 이 문서를 읽을 것.

A batch material-assignment tool, added 2026-07-16 on request ("여러 유형을 한번에 선택해서 재료를 지정"), own ribbon panel/button ("재료 지정"→`MaterialAssignCommand`). `MaterialAssignWindow` deliberately reuses NAMER's proven UI skeleton wholesale (filter textbox + 포함/일치 mode combo, checkbox-row `StackPanel` with drag-to-toggle, pagination, two-stage 적용/최종 적용 with the same "checked-gate only applies to *new* changes, not to changes already committed via 적용" rule) — the only real difference from NAMER is *what* gets changed: an `ElementId` (a `Material`) instead of a `string` (a name). **`FilterTargetCombo`** (added 2026-07-16, on request): a 패밀리/유형-vs-현재 재료 selector next to the filter textbox — `RenderRows()` matches the filter text against `c.Type.Name` or `CurrentMaterialName(c)` depending on its `SelectedIndex`, so a user can search by "which types currently use material X" instead of only by type name; guarded the same `ItemsPanel == null` way as `FilterModeCombo`. **"재료 없음" filter target** (added 2026-07-16, on request — third `FilterTargetCombo` item, index 2): shows only candidates whose `CurrentMaterialId(c) == ElementId.InvalidElementId`, bypassing `FilterBox`/`FilterModeCombo` entirely (a boolean condition has no text to search) — both are explicitly `IsEnabled = false` while this mode is selected, since a filter box/mode a user could still type into but that does nothing would be confusing. **Unused-material labeling** (added 2026-07-16, on request — "패밀리/유형이 지정 안 된 재료도 알아볼 수 있었으면"): `LoadCandidates()` now also builds `_usedMaterialIds` (every `MaterialId` any candidate's slot actually references), and `LoadMaterials()` (which must run *after* `LoadCandidates()` for this) wraps each `Material` in a `MaterialOption{ DisplayName }` appending "(지정된 유형 없음)" for materials no type currently references — shown both in the assign tab's `MaterialCombo` (`DisplayMemberPath="DisplayName"`) and the delete tab's rows (`MaterialDisplayName(m)`), so an orphaned material is now visible and pickable everywhere instead of silently invisible in a tool whose candidate list is fundamentally type-centric. **Confirmed live bug, fixed (2026-07-16)**: `MaterialOption.Material`/`DisplayName` were originally plain fields — `DisplayMemberPath` only binds to *properties* (its reflection lookup is `PropertyDescriptor`-based and simply doesn't see fields), so every row in `MaterialCombo` silently rendered as blank text even though `ItemsSource` genuinely held all the materials — looked exactly like "no materials show up" despite the combo being fully populated. Fixed by making both `{ get; set; }` properties. **Stale-checked-cache fix** (added 2026-07-16, confirmed live — "체크했던 게 캐시처럼 계속 남아있으면 안 된다"): `ApplyButton_Click` used to leave applied rows checked, so picking a *different* material and clicking 적용 again silently re-applied it to those still-checked rows too; it now removes each successfully-applied row's id from `_checkedIds` right after applying.
- **`MaterialSlotFinder`** (shared by the window's display and `MaterialAssignCommand`'s commit): `FindAll(ElementType)` returns *every* "재료 지정" slot on a type, not just one — added 2026-07-22 on request ("여러 재료를 동시에 쓰는 패밀리/유형을 어떻게 지정할 것인가"), replacing the original "exactly one slot or excluded entirely" design. For `HostObjAttributes` types (Wall/Floor/Roof/Ceiling), every non-membrane layer is its own slot (single-layer types like `SplitWallCommand`/`SplitFloorCommand` output still get exactly one, unlabeled, slot — unchanged from before); other types (doors/windows/furniture/framing) get one slot per `Parameter` whose `Definition.GetDataType() == SpecTypeId.Reference.Material` (previously only the *first* such parameter was ever used, silently ignoring the rest). Each `MaterialSlot` carries a `Label` ("레이어 2", or the parameter's `Definition.Name`) that's `""` when a type has only one slot (so the common single-material case looks identical to before) — `MaterialAssignWindow` now shows one candidate row per **(type, slot)** pair instead of per type (`CandidateKey`, keyed on type id + slot identity, replaces the old plain-type-id keying throughout `_checkedIds`/`_candidatesById`/`_workingMaterialIds`), with the row's type name suffixed `· <Label>` when non-empty. `MaterialSlotFinder.Apply`/`FindSlot` re-locate a slot by identity (Kind+LayerIndex or Kind+ParameterId) at commit time rather than trusting a stale reference from when the window was open — same "re-verify at commit time" discipline as before, just slot-aware now. `ChangeLogEntry.SlotLabel` (new, nullable) records which slot a `MaterialAssign` entry targeted so 모델간 변경 반영 (`ChangeReplayEngine`) can re-find the *same* slot by label in the target document (`MaterialSlotFinder.FindSlotByLabel`) instead of just the type — a type-name match alone no longer pins down which slot when a type has several; on a label mismatch the entry is skipped (same "no risky auto-picker" precedent as `MaterialDelete`), not auto-applied to the wrong slot.
- `MaterialSlotFinder.Apply` re-runs `Find` fresh at commit time inside the transaction rather than reusing anything computed while the window was open, and updates only the target material with `CompoundStructure.SetMaterialId` (v95 correction: the previous whole-list `SetLayers` implementation cleared structural metadata; do not restore it). **Resizable columns** (added 2026-07-16, on request): the "재료 지정" tab got the same header-`Grid`-with-named-`ColumnDefinition`s-and-`GridSplitter`s treatment as NAMER (see NAMER's "Resizable name columns" note in `docs/namer/CLAUDE.md` for why plain `Binding`/`DependencyPropertyDescriptor` don't work) — `TypeNameColumn`/`CurrentMaterialColumn`/`NewMaterialColumn`, two splitters, one shared `ColumnSplitter_DragDelta` handler that `UpdateLayout()`s then rewrites all three `TextBlock` widths on every already-rendered row.
- `MaterialAssignCommand`'s transaction also deliberately sets **no custom `IFailuresPreprocessor`**, for the same precautionary reason as `NamerCommand` (see its confirmed-live-bug note in `docs/namer/CLAUDE.md`) even though this hasn't itself been live-confirmed to break here — untested risk, not worth taking for a rarely-warning-triggering metadata edit. **Post-write verification** (added 2026-07-16, on request — "정확하게 모델에 적용이 되었으면 좋겠다"): neither `MaterialSlotFinder.Apply`'s `bool` return nor `Document.Delete`'s lack of a thrown exception is trusted as proof the change actually landed — `ExecuteAssign` re-runs `MaterialSlotFinder.Find` right after applying and compares its `MaterialId` against the intended new material, and `ExecuteDelete` checks that `Document.Delete`'s returned `ICollection<ElementId>` actually contains the target id; either mismatch is now reported in the same failure-summary `TaskDialog` instead of being silently treated as success.
- **"재료 삭제" tab** (added 2026-07-16, on request): a second `TabItem` in the same `MaterialAssignWindow`, independent of the "재료 지정" tab's type list — lists every `Material` in the doc directly (not filtered by any type relationship) with its own filter+mode combo and drag-checkable rows (`DelFilterBox`/`DelItemsPanel`/`DeleteRow`, same copy-pasted drag-select mechanics as the assign tab and `NamerWindow`, since this codebase prefers duplicating the small UI pattern over sharing it across unrelated row types). No pagination here (unlike the assign tab's `PageSize`/"더 보기") since a document's `Material` count is normally far smaller than its `ElementType` count. Deletion has no "computed new value" to preview, so there's no two-stage 적용/최종 적용 — checking rows and clicking "선택한 재료 삭제" goes straight to a Yes/No `MessageBox` confirmation, then closes the dialog with `DeleteResult` set; the actual `doc.Delete(materialId)` calls still happen only afterward, inside `MaterialAssignCommand`'s own transaction (`ExecuteDelete`), same as every other command in this project — the window itself never touches the model. Since a `ShowDialog()` session can only produce **one** outcome, `MaterialAssignCommand.Execute` checks `window.DeleteResult` before `window.Result`/`window.IdentityResult` and dispatches to `ExecuteAssign`/`ExecuteDelete`/`ExecuteIdentityEdit` accordingly (mutually exclusive per invocation — do multiple kinds of operations by reopening the tool again for each).
- **"클래스/설명 변경" tab** (added 2026-07-16, on request — "재료의 아이덴티티의 클래스 및 설명을 변경"): a third `TabItem`, same NAMER-derived filter+mode combo (identical 6-mode `FilterModeCombo` semantics, `IdFilterBox`/`IdFilterModeCombo`) searching `_allMaterials` by name (no pagination, same reasoning as the 재료 삭제 tab). A `IdTargetFieldCombo` (클래스/설명) + one shared `IdNewValueBox` textbox, plus the same 2-stage 적용/최종 적용 (`_trueOriginalClass`/`_workingClass` and `_trueOriginalDescription`/`_workingDescription`, two independent dictionary pairs so a given 적용 click only ever touches whichever one field was targeted) as the 재료 지정 tab. Each row shows both 클래스 and 설명 columns (`IdColumnSplitter_DragDelta`-resizable, same pattern as the other tabs) — whichever column matches the *currently selected* target field, for currently-checked rows with a differing new value, previews as `current → new` in black; everything else shows the accumulated working value in gray, live-updated on every `IdTargetFieldCombo`/`IdNewValueBox` change via `IdRefreshPreview()`. `IdFinalApplyButton_Click` diffs both dictionaries independently and only emits a `(MaterialId, string? NewClass, string? NewDescription)` tuple when at least one field actually changed from its true original — a single material can have only its class touched, only its description, or both, across separate 적용 clicks in one session. `MaterialAssignCommand.ExecuteIdentityEdit` writes `Material.MaterialClass` directly (a real settable property, confirmed via `MetadataLoadContext` reflection of the 2026 `RevitAPI.dll` the same way `Floor.SlabShapeEditor` was checked) but writes 설명 via `Material.get_Parameter(BuiltInParameter.ALL_MODEL_DESCRIPTION)` — **this parameter binding is the best-known candidate (the same general-purpose "Description" field used across many other Identity Data tabs) but is not itself live-confirmed against a real Material's Identity Data tab in Revit; verify live before trusting it**, since reflection can prove a property/enum member exists but not which parameter a given element type actually exposes it as. Same "no custom `IFailuresPreprocessor`, verify by re-reading after Set(), report status/failed-list via `TaskDialog`" pattern as `ExecuteAssign`/`ExecuteDelete`.
