# 설치 프로그램 (SunnyToolsInstaller)

`SunnyToolsInstaller/`를 건드리기 전에 이 문서를 읽을 것. **배포는 반드시 이 설치 프로그램을 퍼블리시해서 하며, Debug/Release DLL을 사용자의 실제 Revit Addins 폴더에 직접 복사하지 않는다.**

`SunnyToolsInstaller/` is a self-contained console app that installs **all 5 year-builds** of `WallSplitter.dll` for end users who don't have this repo, auto-detecting which Revit version(s) they actually have. It's named/branded "Sunny Tools" (not "WallSplitter") since it installs the whole ribbon tab, not just the wall-split command — but the underlying add-in project, assembly, namespace, and Revit `.addin` `<Name>`/`FullClassName` are still `WallSplitter` internally (not renamed; only the installer's own project/output/branding changed on 2026-07-10).

- It does **not** use `ProjectReference` to `WallSplitter.csproj` at all (not even with `ReferenceOutputAssembly="false"`) — instead, an MSBuild `Target BeforeTargets="Build;Publish"` shells out `dotnet build ...WallSplitter.csproj -c Release202X` five times (once per year), then `<None Include="...\net48\*.dll" TargetPath="Payload\202X\%(Filename)%(Extension)">`-style wildcard items copy **every DLL** in each year's output folder (not just `WallSplitter.dll`) into a `Payload\<year>\` subfolder of the installer's own output. This keeps the installer's own dependency graph (and therefore its self-contained publish size) completely unrelated to `WallSplitter.csproj`'s `UseWPF=true` — a plain `ProjectReference` would drag the WPF native runtime into the installer and balloon it from ~30MB to ~65MB zipped for no reason, since the installer process itself never loads WPF, it only copies DLLs as bytes.
  - **Why every DLL, not just `WallSplitter.dll`**: net48 (2023/2024) doesn't ship `System.Text.Json` in the framework, so `NamingSettings`' JSON persistence pulls in `System.Text.Json.dll` + several polyfill DLLs (`System.Memory`, `System.Buffers`, etc.) that NuGet copies alongside `WallSplitter.dll` in the net48 build output. All 5 years also need `Clipper2Lib.dll` for pattern boundary operations. If the installer only copied `WallSplitter.dll`, the affected commands fail before `Execute()` with `FileNotFoundException`. Current expected DLL counts are 2023/2024 각 11개, 2025~2027 각 2개.
- At runtime (`Program.cs`) it checks `C:\Program Files\Autodesk\Revit <year>\Revit.exe` for each of 2023–2027 to detect which versions are actually installed, then for each detected year copies **every file** in `Payload\<year>\` into `%APPDATA%\Autodesk\Revit\Addins\<year>\WallSplitter\` and writes a matching `.addin` manifest there (same `AddInId` as the dev manifest). If detection finds **zero** installed versions (e.g. non-default install path), it falls back to installing all 5 years defensively rather than silently doing nothing. v51부터는 Revit 프로세스가 실행 중이면 파일을 전혀 복사하지 않고 종료하며, 각 연도의 `WallSplitter.dll`과 `Clipper2Lib.dll`이 모두 있는지 복사 전에 검사한다.
- `RuntimeIdentifier=win-x64`, `SelfContained=true`, and `PublishSingleFile=true` are set directly in `SunnyToolsInstaller.csproj` (not passed as `-r`/`--self-contained` flags) so the published output is just `SunnyTools_Install.exe` (+ `.pdb`) instead of the exe sitting among dozens of loose .NET runtime DLLs — added 2026-07-10 after that was reported as hard to find. One consequence: `PublishSingleFile`'s bundler only bundles managed assemblies, not the `Payload\` content folder, and leaves it behind in the intermediate `bin\...\` output — a `Target Name="CopyPayloadToPublishDir" AfterTargets="Publish"` re-copies `$(OutDir)Payload` into `$(PublishDir)Payload` to compensate; don't remove that target or Payload will silently go missing from the publish folder again.
- Distribute via: `dotnet publish SunnyToolsInstaller/SunnyToolsInstaller.csproj -c Release -o <fresh-output-dir>` (RID/self-contained/single-file all come from the csproj now, no need to pass them) → zip that folder's contents (still needs the sibling `Payload\` folder, just no longer needs the exe's old DLL siblings) and send it; recipient extracts the zip and double-clicks `SunnyTools_Install.exe`. A pre-built copy is kept at `SunnyTools_Installer.zip` in the repo root.
- This machine's Desktop folder appears to be watched by some kind of ransomware-canary/decoy-file protection (Windows Controlled Folder Access or similar): publishing ~190+ files in one burst here can transiently spawn an undeletable `*.DOCX` file with garbage attributes in the output folder, which then disappears on its own. If `Remove-Item` on a `bin`/`publish` folder fails with "Invalid File or Directory attributes value", don't fight it — publish to a fresh `-o` directory instead (e.g. `..._v2`, `..._v3`) and ignore the stale one; if it also blocks a wildcard `Copy-Item`/`Get-ChildItem *`, copy files by explicit name instead (the phantom entry breaks glob expansion but not a direct named path).
- **CONFIRMED STALE-PAYLOAD BUG (2026-07-10)**: the `<None Include="..\WallSplitter\bin\Release202X\...\*.dll" CopyToOutputDirectory="PreserveNewest">` items that stage `Payload\<year>\` do **not** reliably pick up a fresh `WallSplitter.csproj` rebuild — confirmed live: after fixing a bug in shared source and rebuilding all 5 `Release202X` configs (verified fresh via direct file timestamps), `SunnyToolsInstaller`'s own `bin\Release\...\Payload\<year>\WallSplitter.dll` still held the pre-fix bytes/timestamp; a fresh `dotnet publish -o` output inherited that same stale copy. Root cause not fully isolated (suspected MSBuild incremental up-to-date caching on the wildcard item, since `bin`/`obj` couldn't be deleted to force a clean rebuild — see the ghost-file issue above), but the fix that worked was to manually copy the real `WallSplitter\bin\Release202X\<tfm>\*` files over the publish output's `Payload\<year>\` by explicit filename, post-publish. **Do not trust `SunnyTools_Installer.zip` (or any fresh publish) to reflect a just-made source fix without verifying `Payload\<year>\WallSplitter.dll`'s timestamp/size against the corresponding `WallSplitter\bin\Release<year>\...\WallSplitter.dll` directly** — silent staleness here means end users (or this machine's own installed add-in) keep running old, already-"fixed" code with zero error signal.
- **LOCKED RELEASE OBJ FALLBACK (2026-08-20)**: 실행 중인 Revit 또는 다른 프로세스가 `WallSplitter\obj\Release20XX\...\WallSplitter.dll`을 메모리 매핑하면 정상 `dotnet publish`의 연도별 Release 빌드가 `CS2012`로 멈출 수 있다. Revit을 강제 종료하지 않고 배포해야 할 때는 각 `Release20XX`를 별도 `IntermediateOutputPath`/`OutputPath`로 빌드하고, `dotnet publish ... -p:SkipWallSplitterPayloadBuild=true`로 `BuildWallSplitterPayload`만 건너뛴다. 그런 다음 별도 출력의 모든 DLL을 새 게시 폴더 `Payload\<year>\`에 명시적 파일명으로 복사한다. 마지막에는 원본 별도 출력과 게시 Payload의 `SHA256`이 모든 연도에서 일치하는지 반드시 확인한다. 이 속성을 썼는데 수동 덮어쓰기/해시 검증을 빼먹으면 오래된 Release DLL이 그대로 배포될 수 있으므로 절대 생략하지 말 것.
- **RUNTIME DEPENDENCY CLOSURE (2026-08-21)**: 빌드 출력과 Payload가 서로 같은지만 비교하면 둘 다 같은 의존 DLL을 빠뜨린 상태에서도 검증이 통과한다. v50이 정확히 이 문제로 2025~2027의 `Clipper2Lib.dll` 없이 배포됐다. `WallSplitter.csproj`의 `CopyLocalLockFileAssemblies=true`를 유지하고, 모든 연도에 `Clipper2Lib.dll`이 있는지 확인한다. net8/net10의 `WallSplitter.deps.json`에 기록된 모든 runtime asset 파일이 실제 격리 출력에 존재하는지도 검사한다. 마지막으로 RevitAPI/RevitAPIUI가 Payload에 들어가지 않았는지 역검사하고, 격리 출력→Payload→ZIP의 정확한 파일 집합과 SHA-256을 비교한다. 설치 프로젝트의 정적 DLL glob은 연도별 빌드 전에 평가될 수 있으므로 `BuildWallSplitterPayload` 안에서 빌드 후 DLL을 다시 열거해 `OutDir\Payload`로 복사하는 동적 단계도 유지한다.

## 최근 배포

- **v80 (2026-09-17, 새 기능: 룸 경계 ON/OFF — 카테고리 단위로 Room Bounding 켜고 끄기)**: 사용자 요청 — "모델에 존재하는 모든 벽, 바닥, 지붕, 기초 등등 룸경계를 결정짓는 모델요소들의 룸경계를 ON/OFF 하는 기능도 추가로 있으면 좋을 것 같아." 리본 패널 이름을 "룸 구분선"에서 **"룸 경계"**로 바꾸고 그 안에 **"룸경계 ON/OFF"** 버튼을 나란히 추가했다(`RoomBoundingCommand`). 창에서 카테고리를 골라 "룸 경계 켜기/끄기"를 누르면 그 카테고리의 모든 요소의 `WALL_ATTR_ROOM_BOUNDING`(룸 경계) 인스턴스 파라미터를 한 번에 바꾼다. **핵심 설계 결정 — 카테고리 목록을 하드코딩하지 않는다**: 룸 경계 파라미터를 가진 카테고리는 벽/바닥/지붕/기초 말고도 천장·기둥·커튼시스템·매스·RVT 링크 등 여럿이고 Revit 버전마다 늘 수 있어, 목록을 적어 두는 대신 **모델 요소를 훑어 그 파라미터를 실제로 가진 것만** 모은다(`CategoryType.Model` + `StorageType.Integer`인 파라미터가 존재하는 요소). 사용자가 말한 "등등"이 저절로 포함되고 새 Revit에서 카테고리가 늘어도 코드를 고칠 필요가 없다 — 화이트리스트로 "최적화"하면 이 성질을 잃으니 하지 말 것. 덕분에 **RVT 링크도 특별 취급 없이 목록에 들어와**, 그 링크가 호스트의 방 경계를 만드는지를 링크 단위로 끄고 켤 수 있다(링크 안의 요소를 바꾸는 게 아니라 링크 인스턴스의 속성이다). 참고: `WALL_ATTR_ROOM_BOUNDING`은 이름이 `WALL_`로 시작하지만 벽 전용이 아니라 바닥·지붕·기둥·링크가 함께 쓰는 공용 파라미터다(오래된 API 이름 — 이름에 속아 벽만 처리하게 만들지 말 것). 그 밖에: 카테고리마다 "켜짐 N · 꺼짐 N · 변경 불가 N"을 보여주고 **"켜짐 0"인 카테고리는 경고색**으로 강조한다("왜 방이 안 나뉘지?"의 원인이 대개 이것), 읽기 전용 파라미터는 건드리지 않고 세어서 보고, 이미 그 값인 요소는 건너뛰어 쓸데없는 워크셋 체크아웃을 만들지 않는다, 요소 하나가 `Set`을 거부해도 예외를 흘리지 않고 계속 처리한다(흘리면 트랜잭션이 통째로 취소돼 "아무것도 안 바뀐다"가 된다), 적용 후 창을 닫지 않고 목록을 다시 읽어 바뀐 상태를 그 자리에서 보여준다. 한 번의 실행이 트랜잭션 하나라 Ctrl+Z로 한 번에 되돌아가며, 룸 경계를 끄면 방이 합쳐지거나 면적이 달라져 일람표·태그까지 영향을 받는다는 경고를 창에 눈에 띄게 적어 뒀다. **검증**: `WALL_ATTR_ROOM_BOUNDING`/`CategoryType.Model`/`Parameter.IsReadOnly`·`StorageType`·`Set`/`Category.CategoryType`/`OST_RvtLinks`가 2023~2027 참조 어셈블리에 모두 존재함을 `MetadataLoadContext`로 확인했고(`API PROBE: ALL PRESENT`), 창은 새 하네스 `RbPreview`로 렌더해 레이아웃을 눈으로 확인했다(카테고리 9종·켜짐/꺼짐/변경 불가 표시·경고 강조 포함). **DLL 심볼 검증의 함정 하나를 새로 기록했다**: `WALL_ATTR_ROOM_BOUNDING`은 enum 멤버라 정수 상수로 컴파일돼 문자열 검색에 안 잡히고, 창 제목 같은 XAML 문자열은 BAML에 들어가 평범한 UTF-16 검색에 안 잡힌다 — 배포 검증에는 **C# 코드의 진짜 문자열 리터럴**(트랜잭션 이름 `룸 경계 켜기` 등)과 타입 이름을 쓸 것. 그 기준으로 5개 연도 전부에서 `RoomBoundingCommand`/`RoomBoundingService`/`CategoryState`/`ApplyResult`/`RoomBoundingWindow`와 `룸 경계 켜기`/`룸 경계 끄기`/`룸경계`를 확인했다. Revit이 실행 중이어서 격리 빌드 경로를 썼고 2023~2027 Release 빌드는 모두 오류 0개다. Payload DLL은 2023/2024 각 11개, 2025~2027 각 2개(총 28개)이며 격리 출력과 파일 집합·SHA-256이 모두 일치했다. 모든 연도에 `Clipper2Lib.dll`이 있고 RevitAPI/RevitAPIUI 재배포는 0개다. 게시 폴더→ZIP 30개 파일의 집합과 SHA-256이 모두 일치했고 ZIP의 만든/수정한 날짜는 배포 시각으로 맞췄다. 설치 실행 파일은 74,045,784 bytes, SHA-256 `FA38376D4A91F8292358AC56684DD42AF32D5DF37B4EF55B9BED2B23742863FF`; 최종 `SunnyTools_Installer.zip`은 30개 파일, 34,435,802 bytes, SHA-256 `4A19987FF6B7024C057DF5FB6B6C0E5512E2011439E88C25BF7A9A47ADA3EC26`. v79 폴더와 ZIP은 `Old_Versions/`에 보관했다. **Revit을 완전히 종료하고 v80을 설치한 뒤 라이브 검증할 것 — (a) 리본 "룸 경계" 패널에 버튼 두 개(룸 구분선 / 룸경계 ON/OFF)가 보이는지, (b) 창을 열면 이 모델의 카테고리와 켜짐/꺼짐 개수가 맞게 나오는지, (c) 끄기/켜기가 실제로 반영되고 방 경계가 그에 맞게 바뀌는지, (d) RVT 링크 항목으로 링크의 방 경계를 끄고 켤 수 있는지.** v79(룸 구분선)의 라이브 검증도 아직이면 같이 확인할 것. 자세한 내용은 `docs/room-separator/CLAUDE.md` 참고.

- **v79 (2026-09-17, 새 기능: 룸 구분선 자동 생성 — 벽 중심선, 링크 모델 포함)**: 사용자 요청 — "지정한 벽체 유형의 중심선에 맞춰서(LINK모델 포함) 룸 구분선을 자동으로 넣어주는 기능을 추가하고 싶다." 리본에 **"룸 구분선"** 패널/버튼이 새로 생겼고(`RoomSeparatorCommand`), 창에서 **벽 유형(다중)** 과 **레벨(다중)** 을 고르면 그 벽들의 중심선 위에 룸 구분선(`OST_RoomSeparationLines`)을 만든다.
