# 화면 디자인 시스템

`WallSplitter/Resources/Theme.xaml`, `WallSplitter/Theme.cs`, 리본 아이콘(`Resources/icon*.png`)을 건드리기 전에 이 문서를 읽을 것. WPF 창 전반에 걸친 네임스페이스 충돌 gotcha(`Visibility`/`Grid`/`Control`/`Color`/`Binding`/`Line`/`Point`)도 여기서 다룬다.

**연혁**: 2026-07-24 다크 테마 최초 도입(강조색 `#5B8DEF`, 둥근 모서리) → 2026-07-27 오전 `Application.Resources` 전역 병합이 Revit 리본/다른 애드인 UI까지 스타일을 물들이는 라이브 버그 발견, 각 창의 로컬 `Window.Resources` 병합으로 수정(아래 "리소스 병합 범위" 참고, 이때 색상 자체는 그대로 다크 유지) → 2026-07-27 오후 **"Industry" 라이트 테마로 전면 교체**(아래 본문) — 현재는 라이트 테마가 최종 상태다. 8개 WPF 창(설정/NAMER/재료 지정/모델간 변경 반영/레이어별 유형 지정/대상 선택/빠른 토글 설정·툴바) 전체가 대상이며, 매번 순수 시각적 변경만 했고 `x:Name`/`Click` 핸들러/이벤트 로직/클래스·파일명은 전혀 건드리지 않았다.

- **리소스 병합 범위**: `Theme.xaml`은 `Application.Resources`가 아니라 **각 창 자신의 `<Window.Resources>`**에 로컬로 병합한다(창마다 `<ResourceDictionary Source="/WallSplitter;component/Resources/Theme.xaml"/>`를 직접 포함). `App.EnsureWpfApplication()`은 이제 `System.Windows.Application` 인스턴스가 없을 때 하나 만들어주는 역할만 한다(복잡한 컨트롤의 기본 템플릿이 테마 리소스 없이는 Baml2006 예외로 실패하는 문제 대응 - 여전히 필요) - 리소스 딕셔너리 자체를 병합하지는 않는다. **왜 전역이 아니라 로컬인가**: Revit은 여러 애드인을 같은 프로세스에 함께 로드하는데, Revit 자신의 리본 UI를 포함해 pyRevit/BIMPeers BIMIL 계열/Metasheet 등도 전부 WPF 기반이라 같은 `Application.Current`를 공유한다 - 우리의 암시적(`TargetType`, `x:Key` 없는) `Window`/`TextBlock`/`Button` 등 스타일을 `Application.Resources`에 병합하면 Revit 리본/다른 애드인 창에까지 그대로 적용돼 그쪽 텍스트까지 우리 테마 색으로 물드는 광범위한 회귀가 있었다(사용자가 "레빗 기존 툴바 텍스트까지 하얘졌다"고 실측 보고, 2026-07-27). `Window.Resources`는 그 창(과 그 창이 띄우는 팝업/드롭다운)의 시각적 트리 안에만 적용되므로 안전하다.
- **2026-07-27, "Industry" 라이트 테마로 전면 교체**: 사용자 요청으로 Claude Design(claude.ai/design, 별도 UI 디자인 도구)에 새 디자인을 의뢰 — 이 저장소를 GitHub(`leesun19990111-cloud/Revitaddin`, `develop` 브랜치)에 연동해 Claude Design이 실제 XAML/PNG 파일을 읽게 했고, Claude Design이 만든 별도 프로젝트("Sunny Tools UI 디자인 개선", claude.ai/design 프로젝트, DesignSync MCP 도구로 `get_file` 읽음)의 `Sunny Tools UI Mockup.dc.html` 목업과 그 안에 포함된 "Industry" 디자인 시스템(`_ds/industry-*/styles.css`+`readme.md`)을 그대로 옮겼다. "Industry"는 밝은 종이 배경(`#F2F2F3`) 위 스틸블루 단일 강조색(`#5980A6`)의 **설계도면(blueprint) 스타일** — 카드/버튼/입력창은 절대 둥글리지 않고(모서리 반지름 0), 얇은 실선 테두리만 두르며, **주 버튼(저장/최종 적용 등)만 강조색으로 채워진 유일한 "입체" 오브젝트**이고 나머지는 채움 없는 "선 그림"이다. 색상값은 `styles.css`의 `:root` 토큰(예: `--color-accent-600`→`AccentHoverBrush`, `--color-accent-700`→`AccentPressedBrush`)을 그대로 옮겼고, 반투명 브러시(`AppBorderBrush`=`#291D1F20` 등)는 CSS의 `color-mix(in srgb, #1d1f20 N%, transparent)` 패턴을 WPF의 ARGB 헥스(`#AARRGGBB`)로 직역한 것이다. **의도적으로 옮기지 않은 것**: (1) 글꼴 — 디자인 시스템은 구글 폰트(Barlow/Barlow Condensed)를 웹 임베드로 쓰지만 이 프로젝트는 외부 CDN/웹폰트에 의존하지 않는다는 기존 원칙이 있어 Windows 기본 글꼴(Segoe UI)로 대체했다(실제 폰트 파일을 리소스로 내장하는 것도 가능은 하지만 이번 범위엔 없음). (2) `.blueprint` 모서리 "+" 등록 마크 장식 — 각 창에 장식용 요소를 추가하려면 창마다 레이아웃(XAML 마크업)을 건드려야 하는데, Claude Design 목업 자체가 "레이아웃/문구는 실제 XAML 그대로, 색·타이포·모서리만 새 테마 기준으로 근사"라고 명시했으므로 색상 시스템(`Theme.xaml`/`Theme.cs`)만 옮기고 레이아웃은 손대지 않았다. (3) 경고/위험 색 — 디자인 시스템 자체엔 "steel 강조색 외 장식색 금지" 원칙이라 별도 토큰이 없는데, 목업이 재료 삭제 버튼에 직접 지정한 값(`#A6595D`)을 그대로 채택하고 Warning은 같은 명도 계열로 새로 골랐다(`#A67B3D`, 디자인 시스템에 지정값 없는 부분이라 이 프로젝트에서 임의 선정). **CheckBox/RadioButton**: 체크박스는 사각형 그대로 유지하되 모서리만 반지름 0으로(디자인 시스템의 `.sqcheck`), 라디오는 원형 그대로 유지했다(readme의 사각 모서리 금지 규칙은 카드/버튼/입력창 같은 "컨테이너" 대상이고, 디자인 시스템 자체에서도 라디오 점은 원형). **비활성 상태 표현 방식이 바뀜**: 예전엔 컨트롤별로 `DisabledBrush`/`DisabledTextBrush`로 색을 바꿔치기했는데, readme가 "비활성 컨트롤은 45% 불투명도로 낮춘다"고 명시적으로 규정해 그 방식 그대로 각 컨트롤 템플릿의 `IsEnabled=False` 트리거를 색 교체 대신 `Opacity="0.45"` 설정으로 바꿨다(더 단순하고 디자인 시스템 규정과 정확히 일치). NamerWindow/QuickToggleSettingsWindow 등의 실제 `RadioButton` 사용은 전부 평범한 가로 나열 또는 세로 목록이라(가로로 촘촘히 붙은 "세그먼트" 그룹이 아님), 목업이 예시로 보여준 알약형 세그먼트 컨트롤(`.seg`+`.seg-opt`)은 창 레이아웃을 건드려야 해서(각 라디오 그룹을 테두리 있는 컨테이너로 감싸야 함) 이번엔 옮기지 않았다 — `RadioButton` 자체는 디자인 시스템의 원형 `.radio` 스타일(체크 시 강조색 채움 원)로만 재도장했다. `Sunny Tools UI Mockup.dc.html`이 렌더링용으로 쓰는 `support.js`/`_ds_bundle.js`(React 기반 프리뷰 런타임)는 Claude Design 안에서 목업을 미리 보기 위한 것일 뿐 실제 산출물이 아니다 — WPF는 HTML/JS를 실행하지 않으므로 실제 구현은 언제나 `Theme.xaml`(XAML)과 `Theme.cs`(코드비하인드 브러시)뿐이다.
- **`WallSplitter/Resources/Theme.xaml`**: 색 팔레트와 `Window`/`Button`(+`PrimaryButtonStyle`/`DangerButtonStyle`)/`TextBox`/`ComboBox`(+`ComboBoxItem`)/`CheckBox`/`RadioButton`/`TabControl`(+`TabItem`)/`ListBox`(+`ListBoxItem`)/`GridSplitter`/`ScrollBar`의 암시적(TargetType) 스타일을 담은 리소스 딕셔너리. **모든 컨트롤을 시스템 기본 테마 리소스에 의존하지 않는 완전 자체 `ControlTemplate`으로 재정의**했다 - 이 프로젝트에서 이미 겪었던 "Application이 없으면 복잡한 컨트롤의 기본(테마) 스타일이 Baml2006 예외로 실패"하는 문제(SettingsWindow 관련 기록 참고)의 근본 원인이 "기본 템플릿이 테마 리소스를 DynamicResource로 참조"하는 것이었으므로, 아예 그 의존성을 없애는 쪽이 각 컨트롤을 색상값으로만 땜질하는 것보다 오히려 더 안전하다고 판단했다. 부수 효과로 net48/net8.0-windows/net10.0-windows(2023~2027) 5개 빌드 사이의 룩앤필도 런타임 기본 테마 차이 없이 완전히 동일해진다. 브러시 `x:Key` 이름 자체는(예: `AccentBrush`, `SurfaceBrush`) 다크 테마 때와 동일하게 유지했으므로 — 값만 바뀌었을 뿐 — 창 XAML 쪽은 전혀 손대지 않고 이 파일 하나만 바꿔서 색을 전면 교체할 수 있었다.
- **`WallSplitter/Theme.cs`**: NAMER/재료 지정/모델간 변경 반영/레이어별 유형 지정 창들이 행을 코드로 생성하며 하드코딩된 색을 쓰지 않도록 하는 `static readonly SolidColorBrush` 모음. **`Theme.xaml`의 같은 이름 토큰과 반드시 수동으로 값을 맞춰서 유지해야 한다** - 두 파일이 색상을 공유하는 자동화된 메커니즘은 없다.
- **주의 - 실측 미검증 지점**: `SettingsWindow`의 토큰 행 이동(▲▼)/삭제(✕) 버튼은 `CreateTriangle`/`CreateXMark`가 직접 그린 도형이다. 다크 테마 때는 `Theme.TextPrimary`(밝은 색)로 어두운 버튼 배경 위에서 보이게 했었는데, 라이트 테마로 바뀌며 버튼 배경이 다시 밝아졌으므로 도형 색도 `Theme.TextPrimary`(이제는 어두운 `#1D1F20`)로 자동으로 대비가 유지되긴 하지만, **실제 Revit에서 육안 확인 전까지는 미검증**이다 - 안 보인다는 보고가 있으면 이 지점부터 확인할 것.
- **리본 아이콘 7종 리컬러 (2026-07-27, 사용자가 "아이콘도 디자인이 적용 안 된 것 같다"고 재요청해서 추가)**: 처음 Industry 테마를 옮길 때는 아이콘을 손대지 않았었다(목업의 아이콘 미리보기 섹션도 기존 PNG를 그대로 불러와 보여줄 뿐 새로 디자인하지 않았으므로). 이후 사용자 요청으로 `WallSplitter/Resources/icon*.png`(16px/32px, 총 16개 - 빠른 토글/모델간 변경 반영 아이콘 포함) 전부를 새 강조색(`#5980A6`)으로 다시 칠했다. 스크래치패드의 1회성 `System.Drawing` 도구로 먼저 각 PNG의 실제 픽셀 RGB 분포를 조사해(알파>0인 픽셀만) 전부 옛 강조색(`#5B8DEF`) 근방 몇 hex 이내로만 갈리는 단색 line-art임을 확인한 뒤(안티앨리어싱 잔여물일 뿐 의도된 다색 아님), 알파(경계 부드러움)는 그대로 두고 RGB만 새 강조색으로 일괄 치환했다 - 도형을 다시 그린 게 아니라 기존 실루엣의 색만 바꾼 것이라 모양은 완전히 동일하다. **GDI+ 함정**: `Bitmap`을 파일 경로로 직접 생성자에 열어둔 채로 같은 경로에 `Save()`하면 "GDI+에서 일반 오류가 발생했습니다"로 실패한다 - 원본을 `File.ReadAllBytes` + `MemoryStream`으로 먼저 메모리에 읽어 파일 잠금을 끊어야 같은 경로에 안전하게 덮어쓸 수 있다.
