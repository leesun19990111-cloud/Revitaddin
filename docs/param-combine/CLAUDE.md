# 매개변수 조합 (여러 매개변수를 합쳐 자동 기입)

`ParamCombine*.cs`를 건드리기 전에 이 문서를 읽을 것. 이 기능은 이 저장소에서 **유일하게 Revit의 Dynamic Model Update(`IUpdater`)를 쓰는 곳**이라, 다른 기능의 감각(명령 안에서 트랜잭션을 열고 끝낸다)이 여기서는 통하지 않는다.

> **이름 주의**: 리본/창에 보이는 이름은 **"매개변수 조합"**, 코드의 클래스·파일 접두사는 **`ParamCombine`**, 문서 폴더는 `docs/param-combine/`다. 2026-09-22에 이름을 두 번 바꿨다 — 처음 낸 **"자동 결합"** 은 사용자가 *"모델링 요소를 결합하는 느낌이라"*(Revit의 Join과 헷갈림) 거부했고, 다음으로 붙인 **"매개변수 수식"** 도 사용자가 **"매개변수 조합"** 으로 다시 바꿨다. 클래스 이름(`ParamCombine*`)은 일부러 그대로 뒀다 — 커스텀 버튼의 "기능 버튼" 설정이 `IExternalCommand`의 **클래스 FullName**을 저장하므로(`SunnyToolsCommands.All`), 클래스를 개명하면 이미 등록된 버튼이 조용히 깨진다. 영어 "Combine"은 지금 이름 "조합"과도 그대로 맞고 Join과 헷갈릴 여지가 없다.

## 무엇이고, 왜 만들었나 (2026-09-22)

사용자가 ChatGPT와 나눈 대화(`Dynamo 실번호 자동입력`)를 가져와 "이 대화로 만들 수 있는 Dynamo 기능을, 값이 바뀌면 자동으로 연동돼 최종값도 실시간으로 달라지는 애드인으로 만들고 싶다"고 요청한 것이 출발점이다.

그 대화의 상황:

- 일람표에서 `용도 + 지상지하 + 층 + 번호` 4개 매개변수를 Revit의 **결합된 매개변수(Combined Parameter)** 로 묶어 `XX00000` 형식으로 보고 있었다.
- 그런데 그 값은 **일람표에서만 만들어지는 표시값**이라 룸 객체에는 저장되지 않는다.
- 그래서 Dynamo로 `All Elements of Category(Rooms) → Element.GetParameterValueByName × 4 → Code Block(a+b+c+d) → Element.SetParameterByName(실번호)` 그래프를 만들어 실제 값으로 써넣는 데까지 성공했다.
- 대화가 짚은 두 가지 한계가 이 애드인의 존재 이유다:
  1. **자리수 문제** — `층`/`번호`가 숫자 매개변수면 Revit 내부에는 `1`, `3`으로 저장돼 있어 단순 결합이 `XX13`이 된다. `XX01003`을 원하면 zero padding이 필요하다.
  2. **실시간이 아니다** — 대화의 원문: *"현재 Dynamo는 자동 실시간 연동은 아니야. 번호 001 → 002를 수정해도 실번호가 알아서 즉시 OB01002로 바뀌는 것은 아니고, Dynamo를 다시 Run해야 갱신돼."* 대화가 제시한 최선의 해법은 "Dynamo Player에서 버튼 한 번 누르기"였다.

**Dynamo에는 없고 Revit API에는 있는 것이 `IUpdater`다.** 그래서 이 기능은 Dynamo 그래프를 옮겨 적은 것이 아니라, 그 그래프가 구조적으로 못 하는 부분(버튼을 누르지 않아도 되는 진짜 연동)을 채우는 방향으로 만들었다.

## 사용자가 정한 것 (2026-09-22, 질문해서 확정)

- **자리수 기본값**: 용도 1 + 지상지하 1 + 층 2 + 번호 3 → `XX01003`(총 7자리). 설정 창에서 언제든 바꿀 수 있고, 이건 처음 열었을 때의 기본값일 뿐이다.
- **범위**: 룸 전용이 아니라 **카테고리를 설정에서 고르는 범용 기능**으로 만든다. 소스 매개변수도 개수 제한 없이 자유롭게 추가한다.
- **대상 매개변수가 없을 때**: 경고만 띄우고 아무것도 하지 않는다. **애드인이 공유 매개변수 파일을 대신 만들거나 고치지 않는다** — 회사 표준 공유 매개변수 파일을 건드리는 위험이 편의보다 크다는 판단. 이 결정을 되돌리려면 사용자에게 다시 물을 것.

## IUpdater를 쓸 때 반드시 지킬 것

- **`Execute` 안에서 트랜잭션을 열지 않는다.** 이미 사용자의 트랜잭션 안이다. 그래서 `ParamCombineEngine`은 트랜잭션을 모르는 순수 계산부로 분리했고, 트랜잭션은 "전체 갱신" 명령과 설정 창의 "저장 후 전체 적용"에서만 연다.
- **`Execute`에서 예외를 밖으로 내보내지 않는다.** Revit이 업데이터 실패 대화상자를 띄우거나 업데이터를 꺼버린다(`App.cs`의 다른 Revit 이벤트 콜백들과 같은 방침).
- **무한 루프 방지는 두 겹이다**: ① `_running` 정적 재진입 플래그, ② `ParamCombineEngine.Apply`가 "값이 이미 같으면 아무것도 쓰지 않고 반환". ②가 본질적인 안전장치라 ①만 믿지 말 것 — 자기가 쓴 값 때문에 다시 불려도 두 번째 패스에서 즉시 수렴한다.
- **`DocumentChanged`로 대체할 수 없다.** `DocumentChanged`는 트랜잭션이 **끝난 뒤** 오는 읽기 전용 알림이라 거기서 모델을 고칠 수 없다(경고Pick이 목록 갱신에만 쓰는 이유). `IUpdater`만이 사용자의 그 트랜잭션 **안에서** 값을 같이 고칠 수 있고, 그래서 Ctrl+Z 한 번에 소스와 결과가 함께 되돌아간다.
- **등록은 `App.OnStartup`에서 `application.ActiveAddInId`로 한 번만**, 해제는 `OnShutdown`에서. `RegisterUpdater(updater, true)`의 `isOptional=true`는 이 애드인이 없는 PC에서 그 모델을 열어도 Revit이 항의하지 않게 한다.
- **트리거는 문서 단위**라 `DocumentOpened`/`DocumentCreated`마다, 그리고 설정이 바뀔 때마다 `RefreshTriggers`로 다시 붙인다. 문서 이벤트 구독은 **`App.OnStartup`의 `ControlledApplication`에서만** 한다(루트 `CLAUDE.md`의 NAMER 크래시 항목과 같은 이유).

### 왜 `GetChangeTypeAny()`인가 (매개변수별 트리거를 쓰지 않는 이유)

`Element.GetChangeTypeParameter(paramId)`로 소스 매개변수만 감시하면 훨씬 적게 불릴 텐데, 그러려면 그 매개변수의 `ElementId`가 필요하다. 그런데 규칙은 **이름**으로만 적혀 있고, 내장 매개변수(룸의 `번호`=`ROOM_NUMBER`)·공유 매개변수·프로젝트 매개변수가 섞여 들어오며, 사용자가 아직 없는 이름을 적어둘 수도 있다. 하나라도 해석에 실패하면 그 변경을 조용히 놓치는데, 그러면 "실시간 연동"이라는 이 기능의 핵심이 무너진다. `GetChangeTypeAny()` + `GetChangeTypeElementAddition()`은 조금 더 자주 불리지만 `Apply`가 "값이 같으면 즉시 반환"이라 비용이 사실상 없다. **성능이 문제가 되어 매개변수별 트리거로 바꾸고 싶어지면, 해석 실패 시 `GetChangeTypeAny`로 떨어지는 fallback을 반드시 같이 넣을 것.**

## 값 읽기/쓰기 규칙

- **읽기**는 인스턴스 → 없으면 유형 매개변수까지 찾는다(용도/지상지하를 유형 매개변수로 만들어 둔 프로젝트가 있다 — 읽기만 하므로 안전).
- **쓰기 대상은 반드시 인스턴스 매개변수**다(`FindWritableParameter`는 `LookupParameter`만 쓴다). 유형 매개변수에 쓰면 같은 유형을 쓰는 다른 요소가 전부 같이 바뀐다.
- 대상은 `StorageType.String`이어야 한다. 아니면 `TargetNotText`로 세어 건너뛴다.
- **숫자는 `AsValueString()`이 아니라 숫자 자체로 읽는다** — `AsValueString`에는 단위 기호와 천 단위 구분자가 섞여 있어 실번호에 못 쓴다. 자리수 채움의 대상이 되는 것도 숫자 쪽이다(`층 1 → "1" → "01"`).
- `StorageType.ElementId`는 참조 요소의 이름을 쓴다(룸의 `레벨`을 소스로 쓰면 레벨 이름이 들어온다).
- **자르기(Truncate)의 기본은 꺼짐**이다. 번호 `1234`를 3자리로 자르면 어느 쪽을 버려도 틀린 값이 되므로, 조용히 뭉개는 것보다 길어진 채로 눈에 띄는 편이 낫다.

## 설정 창에서 의도적으로 막아 둔 것

- **결과 매개변수를 소스로도 쓰는 규칙은 저장을 거부한다** — 자기 값을 자기가 덮어쓰며 계속 흔들린다.
- **매개변수 이름은 타이핑이 아니라 목록에서 고른다.** ChatGPT 대화에서도 *"Revit에 실제 적혀 있는 매개변수 이름과 한 글자까지 동일해야 한다"* 가 이 기능의 첫 번째 함정으로 지적됐다. 목록은 그 카테고리의 표본 요소 하나를 훑은 결과(내장 매개변수까지 전부 나온다) + `doc.ParameterBindings`에 그 카테고리로 바인딩된 공유/프로젝트 매개변수(요소가 아직 하나도 없어도 나온다)를 합친 것이다. 설정에 저장돼 있는데 목록에 없는 이름은 목록 맨 앞에 그대로 끼워 넣어 **조용히 다른 값으로 바뀌지 않게** 한다(카테고리도 같은 방식).
- 마지막 소스 줄의 "구분자" 입력칸은 비활성이다 — 결과에 쓰이지 않으므로("왜 안 붙지?"를 미리 없앤다).

## 설정 창 "합칠 매개변수" 표의 열 정렬 (되돌리지 말 것)

**CONFIRMED UI BUG (2026-09-22, 사용자 제보 — "자리수/채움/채울위치/자르기/구분자 열이 아래 요소들과 열이 맞지 않아서 헷갈려")**: 이 표는 머리글과 각 줄이 **저마다 독립된 `Grid`** 다(공통 `Grid` 하나에 행을 쌓는 구조가 아니다 — 줄 추가/삭제/이동이 잦아 통짜 Grid로는 다루기 번거롭다). 처음에는 일부 열을 `GridLength.Auto`로 뒀는데, `Auto`는 **그 Grid 안의 내용**으로만 폭이 정해지므로 머리글(`"자르기"` 같은 글자)과 내용 줄(체크박스 하나)의 폭이 달라져 열이 어긋났다. 머리글에 라벨이 없던 ▲▼✕ 칸은 아예 폭 0이 되어 어긋남이 더 커졌다.

**수정**: `SourceColumnWidths`(첫 칸만 Star, 나머지는 전부 고정 px) 하나를 머리글과 모든 줄이 공유한다. 고정 폭이 같으면 Star 칸의 폭도 모든 Grid에서 같게 계산되므로 완전히 정렬된다. **이 열들을 다시 `Auto`로 되돌리지 말 것.** 열을 추가할 때는 `SourceColumnWidths`에 폭을 넣고 머리글 `Label(...)`과 줄의 `WpfGrid.SetColumn(...)` 인덱스를 함께 옮길 것(현재 10개: 매개변수 / 자리수 / 채울 문자 / 채울 위치 / 자르기 / 구분자 / 예시 / ▲ / ▼ / ✕). WPF의 `Grid.IsSharedSizeScope` + `SharedSizeGroup`으로도 풀 수 있지만, 고정 폭이 더 단순하고 이 표는 열 폭이 내용에 따라 늘어날 이유가 없다.

같은 제보의 두 번째 항목 — **"채움이 뭔지 모르겠어"**. 열 이름을 `채움` → `채울 문자`로 바꾸고, 표 위에 한 줄 설명(층 값이 1인데 자리수 2, 채울 문자 0, 채울 위치 앞이면 01)을 넣고, **줄마다 `예시` 칸**을 추가했다. 예시는 그 카테고리의 표본 요소(`ParamCombineEngine.SampleElement`)에서 읽은 **실제 값**으로 `1 → 01`처럼 보여주고, 읽을 값이 없을 때만 `예) 1 → 01`처럼 임시 값을 쓴다. 갱신은 줄마다 `_rowExampleUpdaters`에 등록해 두고 `RefreshPreview`가 한꺼번에 호출한다 — 입력 핸들러가 이미 전부 `RefreshPreview`를 부르므로 핸들러마다 따로 갱신 코드를 넣지 않아도 된다.

## 기본 설정이 "실시간 꺼짐"인 이유

`ParamCombineSettings.Load()`의 **기본값은 `AutoUpdate = false`** 다(규칙은 `실번호` 기본 규칙 하나가 들어 있다). 설정 파일이 없는 첫 실행에서 곧바로 자동 기입이 시작되면, 그 사용자의 매개변수 이름이 기본 규칙과 맞는지 확인하기도 전에 모델을 고치게 된다. 설정 창에서 미리보기로 확인한 뒤 직접 켜게 하는 것이 맞다. **이 기본값을 `true`로 바꾸지 말 것.**

리본 토글로 **켤 때는 그 자리에서 전체 갱신을 한 번 돌린다** — 켜기 전에 있던 값들은 아직 옛날 값이라, 켜자마자 맞춰주지 않으면 "켰는데 왜 안 바뀌지?"가 된다(앞으로의 변경은 `IUpdater`가 따라간다).

## 알려진 한계

- 작업공유 모델에서 다른 사용자가 소유한 요소에는 쓸 수 없다(`Failed`로 세어 결과에 표시).
- 소스가 **링크 모델**에 있는 값이면 읽을 수 없다. 규칙은 이 문서 안의 요소만 본다.
- 카테고리 목록은 `AllowsBoundParameters`인 **내장 카테고리(음수 id)** 만 담는다 — 사용자 정의 하위 카테고리는 문서마다 id가 달라 설정 파일에 저장할 수 없기 때문이다.
- 설정은 `%APPDATA%` 전역이라 프로젝트별로 다른 규칙을 쓸 수 없다(커스텀 버튼 설정과 같은 방침).
