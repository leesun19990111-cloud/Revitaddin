# 멀티 버전 빌드 (Revit 2023–2027)

`WallSplitter.csproj`의 연도별 Configuration→TFM→`Nice3point.Revit.Api.RevitAPI` 패키지 버전 매핑을 건드리기 전에 이 문서를 읽을 것.

`WallSplitter.csproj` builds the **same source** against 5 different Revit API versions via custom per-year Configurations, not `<TargetFrameworks>` (a single project can't multi-target the same TFM twice, and 2025/2026 share `net8.0-windows` while still needing different `RevitAPI.dll` versions):

- Configurations are named `Debug2023`/`Release2023` … `Debug2027`/`Release2027`. `WallSplitter.csproj` reads the trailing 4 digits into an MSBuild `$(RevitVersion)` property, which drives `$(TargetFramework)`; the `Nice3point.Revit.Api.RevitAPI`/`RevitAPIUI` NuGet package version is resolved from `$(RevitApiPackageVersion)` (see next bullet — no longer a bare `$(RevitVersion).*-*` wildcard for every year).
- **CONFIRMED LIVE BUG (2026-07-27), fixed**: the original `Version="$(RevitVersion).*-*"` wildcard lets NuGet pick whatever is the *newest* Nice3point patch for that year at restore time, which can silently drift ahead of the Revit build actually installed on a given machine. Live-confirmed: this machine's installed Revit 2026 ships `RevitAPI.dll`/`RevitAPIUI.dll` at file version `26.4.0.32` (checked via `(Get-Item ...RevitAPI.dll).VersionInfo.FileVersion`), but a `dotnet restore` had pulled Nice3point package `2026.4.10` (assembly version `26.4.10.0`) — one patch ahead. This mismatch does **not** break plain Revit API calls (confirmed: 벽체 분리 with no picker dialog still ran fine), but it reliably threw inside every command that opens a WPF window — NAMER/재료 지정/모델간 변경 반영/빠른 토글 설정 all failed with Revit's generic "외부 명령을 완료할 수 없습니다" dialog, root-caused via the Revit journal (`%LOCALAPPDATA%\Autodesk\Revit\Autodesk Revit 2026\Journals\journal.*.txt`, which recorded `API_ERROR: Assembly version conflict ... Addin's module RevitAPIUI of version 26.4.10.0 conflicts with same preloaded module of version 26.4.0.0` followed by a `XamlReader.RewrapException` stack trace through `Application.LoadComponent`/`<Window>.InitializeComponent()`) — i.e. BAML/XAML loading fails strict-checking the referenced assembly version in a way plain DB/UI API calls don't. Fixed by pinning `$(RevitApiPackageVersion)` to an exact package version per year *for years this machine can verify installed* (`2023.1.90` for 2023, `2026.4.0` for 2026 — both confirmed to match the installed `RevitAPI.dll` FileVersion exactly), falling back to the old wildcard only for years not installed here (2024/2025/2027, unverifiable on this machine). **If this same symptom (window-opening commands fail, non-window commands like plain 벽체 분리 still work) is ever reported for 2024/2025/2027, diagnose the same way** (check that year's Revit journal for "Assembly version conflict", compare the installed `RevitAPI.dll` FileVersion via PowerShell against the currently-restored Nice3point package version) and pin that year's `RevitApiPackageVersion` condition to the exact matching package version too — don't just bump to "latest" again.
- **Empirically confirmed** (by restoring the Nice3point packages and diffing reflected API surface across the 2023 and 2027 packages — not guessed): 2023 & 2024 → `net48`; 2025 & 2026 → `net8.0-windows`; 2027 → `net10.0-windows`. If Autodesk ships a Revit 2028, check its actual required TFM the same way (restore `Nice3point.Revit.Api.RevitAPI` at `2028.*-*` against candidate TFMs and read the `NU1202`/no-warning result) before assuming it follows the same pattern.
- All Wall/Sketch/Curve/Transform/Plane/Ribbon APIs this project uses were verified identical across the 2023 and 2027 packages, so most of the source is shared as-is across all 5 years with no conditional compilation. One exception exists (`Floor.SlabShapeEditor`, see `SplitFloorCommand.cs` in `docs/wall-floor-split/CLAUDE.md`): when a future API call turns out to differ by year, gate it with `#if REVIT20XX`/`#if REVIT20XX_OR_GREATER`-style constants defined in a `DefineConstants` `PropertyGroup` keyed off `$(RevitVersion)` (Nice3point's SDK generates these automatically; since we don't use their SDK, add each constant by hand, only for the specific years actually needed — don't pre-define the full matrix speculatively).
- We use the **`Nice3point.Revit.Api.RevitAPI`/`RevitAPIUI` NuGet packages** (not local `Program Files\Autodesk\Revit <year>\` HintPath references) specifically so the project builds for all 5 years even though this machine only has Revit 2023 and 2026 actually installed. These are `ref/`-only (compile-time) packages and are never copied to output.
- We deliberately did **not** adopt `Nice3point.Revit.Sdk` (the custom MSBuild SDK that automates this exact Configuration→TFM→package wiring, used by their official templates) — the mapping above is hand-rolled in plain `Microsoft.NET.Sdk` `PropertyGroup` conditions to keep the build fully transparent/inspectable, consistent with how the rest of this repo avoids extra abstraction. Revisit that decision if maintaining the per-year conditionals by hand becomes painful.
- `<LangVersion>latest</LangVersion>` is required — `net48` alone defaults to C# 7.3, which breaks `Nullable`/target-typed patterns used in the shared source.
- Build one year: `dotnet build WallSplitter/WallSplitter.csproj -c Release2026`. Output lands in `WallSplitter/bin/Release2026/net8.0-windows/WallSplitter.dll` (folder name includes the year since Configuration is part of the default output path).
